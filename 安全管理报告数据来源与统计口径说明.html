安全管理报告数据来源与统计口径说明

版本：2026-11-04｜依据：当前本地原型实际代码｜适用页面：安全管理报告.html

本文说明页面、报告预览和下载报告中的数据从哪里来、如何计算。说明以代码当前行为为准；“正式系统建议”不代表原型已实现。本文未修改页面业务逻辑。

1. 先明确当前数据性质

当前安全管理报告使用原型演示数据，不是生产接口数据。生成报告时，buildReport() 强制将来源设为 demo，通过 StatsEngine.load('demo') 读取数据。即使后续页面增加来源选择，当前这段逻辑仍固定使用演示数据。

数据来源当前提供的内容读取方式与用途
统计数据引擎.js → demo()最近95天的模拟AI报警，每天5～10条；包含时间、类型、区域、等级、责任人、复核、接收和处置时间按当前日期动态构造，支撑报告指标及对比
报警演示数据.js、今日报警演示数据.js → ALARM_DEMO_RECORDS其中的消防设备报警记录只将符合消防来源判断的记录追加到上述模拟AI数据；不会把全部AI报警中心记录追加进来
责任区域数据.js → ResponsibilityData人员、部门、区域基础数据为模拟记录分配责任人、部门；模拟AI区域来自引擎内固定的6个区域路径
基础配置规则.js → AlarmBasicSettings.get()复核与处置超时时限读取浏览器 alarm-basic-settings-v1；缺省复核300秒、处置1800秒
浏览器 localStorage → sinotrans-safety-reports-v1已生成的报告快照报告列表、预览、下载均读取快照，不在预览时重新计算
浏览器 localStorage → sinotrans-safety-schedules-v1日报、周报、月报开关控制页面在线时的自动检查；不是后台定时任务

因此：报告数据不一定等于AI报警中心或查处管理当前列表的数据。 当前 demo 分支不会读取本地真实操作保存的接收、处置记录，也不会读取报警中心新增记录。引擎虽有其他读取分支，但安全管理报告生成未使用该分支。

2. 报告的统计范围和时间

所有报告按记录的 time 字段归属周期，起止时间均包含在内。当前报告引擎并未统一将消防时间替换为查处列表中的“平台首次接收时间”；两处取值不能自动视为完全一致。

项目数据来源与取值规则
日报周期前一自然日00:00:00至23:59:59.999
周报周期前一完整自然周，周一00:00:00至周日23:59:59.999
月报周期前一完整自然月，月初至月末
自定义周期用户选择的起止时间；结束不能晚于当前时间，跨度不超过366天
对比周期紧邻当前周期之前、毫秒长度完全相同的一段时间。起点=本期起点−本期长度；终点=本期起点−1毫秒
状态截止时间报告生成时；先按报警时间选记录，再读取当时的复核及处置状态

月报对比是“上一等长时段”，不保证等于上一个自然月。例如31天的月报，会向前取31天，而不是固定取前一个月。

4. 报告顶部四个指标

以下所有计算均在当前报告周期记录内进行。

指标数据字段/来源实际计算口径
报警总量metrics.total周期内全部记录数，包含模拟AI报警和追加的消防设备报警
识别准确率metrics.accuracy确认违规数 ÷（确认违规数＋误报数）×100%；无分母显示“—”
闭环率metrics.closeRate已闭环数 ÷ 应查处数 ×100%；应查处=AI确认违规记录＋消防设备报警记录；无分母显示“—”
处置超期metrics.disposalLate应查处记录中被判定处置超期的数量，包含已完成后超期和仍未完成的超期记录

百分比先计算再四舍五入到小数1位，整数时可能显示为100%而不是100.0%。合计按全部记录重新计算，不取分组百分比平均值。

4.1 基础分类怎样判定

分类实际判定条件
AI确认违规status='已复核'且result='确认违规'
误报status='已复核'且result='误报'
计划内事件status='已复核'且result='计划内事件'
疑似status='已复核'且result='疑似'
待复核非消防记录且status!='已复核'
AI已闭环AI确认违规，且有有效disposal.time，时间不晚于报告生成时
消防已闭环消防状态为已处置、已恢复、完成处理或已闭环之一
应查处AI确认违规或消防设备报警；消防记录不计入confirmed，但计入闭环率分母

实现细节：误报、计划内事件、疑似这三个计数判断没有额外排除消防来源。当前演示消防数据通常不会触发这些分类；正式接入时应限制这些字段用于AI复核，避免消防结果值误入准确率计算。

4.2 处置超期如何计算

AI记录：必须已经确认违规并已接收。以接收时间 receipt.time 为起点，完成记录计算至 disposal.time，未完成记录计算至生成时。用时严格大于配置的 disposalSeconds 才计超期，等于不计。缺少有效接收时间时不会按此规则计超期。

消防记录：当前不按时间自动推算，而读取同步标记：disposalLate=true，或disposalOverdue=true / '是'，或disposalOverdue以“超期”开头。没有标记时不计超期，不能据此认定外部业务一定未超期。

5. “一、总体情况与周期比较”

正文中的确认违规、误报、计划内事件、疑似、待复核、已闭环，分别取 metrics.confirmed / mis / planned / suspected / pending / closed，与上节定义相同。

对比项公式边界处理
报警量较上一等长时段（本期报警量−上期报警量）÷上期报警量×100%上期为0且本期也为0：显示持平；上期为0、本期非0：显示“上一等长时段为0”
准确率变化本期准确率−上期准确率单位为“个百分点”，不是增长百分比；任一无有效分母显示“暂无可比数据”
闭环率变化本期闭环率−上期闭环率同上，保留1位小数

两期都在本次生成报告时读取并归一化状态。这里不是将上一份历史报告的数值直接拿来比较，所以旧周期的后续处置变化可能影响新报告中的对比值。

对照用户截图的数字

截图报告周期为2026-11-03：报警总量6条、确认违规6条、误报0条、已闭环4条。

• 准确率：6÷(6＋0)=100%。

• 闭环率：4÷6≈66.7%（该日报周期没有追加消防记录）。

• 处置超期1条：有1条记录满足上述超期规则，不能仅从“未闭环2条”推导出来。

• 报警量变化−14.3%：对比期7条，本期6条，(6−7)÷7≈−14.3%。

• 准确率变化＋28.6个百分点：100%−71.4%=28.6个百分点。

• 闭环率变化−13.3个百分点：66.7%−80%=−13.3个百分点。

以上数字是对截图的公式解释，不代表实时生产数据；其他周期或新生成报告可能不同。

6. “二、重点区域”每个数据的来源

先选出AI确认违规记录，按 area 路径分组，再按确认违规数量降序排序，仅展示前5个区域。它不是全部区域清单，也不是所有报警数量的排行。

列来源和计算
区域记录的area；如“2#仓库 / 1层 / 货架区”；缺少值显示未分配
确认违规该区域的AI确认违规数量
已闭环该区域这些AI确认违规记录中已完成处置的数量
闭环率该区域已闭环数÷该区域AI确认违规数×100%

消防记录当前不进入这张表；因此不能要求“重点区域”已闭环数量相加等于报告顶部已闭环数。即使只有AI，Top5截断也可能导致二者不相等。并列数量没有额外的风险评分排序规则。

报告生成不读取区域配置页面新设置的责任人重新归属区域，也不使用最新消防报表的“只显示二级区域”规则；该报告目前按记录原始完整区域路径分组。

7. “三、违规事件类型表现”每个数据的来源

将本期全部记录按原始 type 分组，按报警总量降序，仅展示前6种类型。

列来源和计算
违规事件类型记录原始type；缺少值显示未分配
报警量该类型全部记录数，可能包含消防记录
确认违规该类型AI确认违规数
误报该类型已复核且结果为误报的数量
计划内事件该类型已复核且结果为计划内事件的数量

准确率该类型确认违规÷(该类型确认违规＋误报)×100%；无分母显示“—”

Top6之和可能小于总量。当前分组直接使用原始type，并未套用查处管理消防名称转换，也没有将火警、预警、故障、隐患、动作、离线六类作为这里的分组维度。不要把两个页面的标签自动理解为同一统计字段。

8. “四、重点问题与改进建议”的来源

当前是 StatsEngine.insights() 的固定规则拼接，没有调用大模型，也没有读取知识库或人工评审结果。

触发条件生成内容
总量大于0期间报警、确认违规、误报、计划内事件、疑似数量概述
没有报警期间无报警，暂无可分析数据
有AI确认违规已闭环、闭环率和待闭环数量提示
存在AI确认违规区域选确认违规数最多的区域，建议优先核查作业及防护措施
有待复核记录提示先完成复核，再评估准确率
有处置超期记录提示核实责任人和整改进度
有误报记录提示按类型和场景复查样本、调整识别策略

待闭环数量=待接收AI数＋待处置数；后者包含未闭环消防记录。当前建议文字写“确认违规已闭环”，但其中closed在有消防记录时也会包含消防已闭环，文案与范围存在差异。建议内容用于辅助说明，不能认定为自动安全结论。

9. 周期自动生成提示与实际行为

类型当前页面提示当前计算的报告周期
日报每日09:00后自动生成前一自然日
周报每周一09:00后自动生成前一完整自然周
月报每月1日09:00后自动生成前一完整自然月

实际检查逻辑：页面打开后及每60秒检查一次；浏览器当前小时必须不小于9；开关开启；相同类型、来源和周期起点已经有自动报告则跳过。

目前代码没有强制检查“今天必须周一”或“今天必须1日”。例如周三开启周报，若上周尚无自动报告，也会生成上周报告。这更接近页面在线时补生成最近完整周期。此前修改的是提示文案，尚未将执行条件改为严格指定日期。

页面关闭时不会自动执行；开关也不会启动后台服务。正式系统应由服务器定时任务执行，并明确错过周期后的补生成策略。

11. 正式接口最少需要提供什么

下表为接入建议，不表示当前已有接口。

数据对象必要字段支撑内容
报警事件alarmId、sourceType、eventTime、firstReceivedAt、typeCode/typeName、areaId/areaPath、deviceId、level去重、来源识别、周期归属、区域和类型分组
AI复核alarmId、reviewStatus、reviewResult、reviewTime、reviewerId确认违规、误报、计划内事件、疑似、待复核、准确率
AI查处alarmId、receiptTime、disposalStatus、completedAt接收、闭环、超期及用时
消防处置同步alarmId、eventCategory、disposalStatus、completedAt、disposalLate、overdueRule消防闭环与超期，避免把离线或不适用状态全部视为待处置
区域和人员字典areaId、层级路径、departmentId、personId统一分组与责任归属；明确采用报警时还是当前归属
基础时限配置reviewSeconds、disposalSeconds、生效时间/版本可追溯超期判断
报告快照reportId、kind、rangeStart/rangeEnd、generatedAt、source、metrics、previous、areas、types、notes、ruleVersion复现历史报告、审计与跨设备读取
调度记录scheduleType、plannedAt、executedAt、success、补生成标记证明自动报告实际生成时间和执行结果

正式系统应先按alarmId明确去重及关联规则，再汇总；当前演示分支只是拼接数组，不提供跨系统去重保证。
